## One-time setup

1. Visual Studio 2022 with *Desktop development with C++*, *C++ Clang Compiler for Windows* and
   *MSBuild support for LLVM (clang-cl)*. This provides Clang 19, CMake 3.31 and Ninja.
2. ReXGlue SDK built and installed at `C:\dev\rexglue-sdk`:
   ```powershell
   git clone https://github.com/rexglue/rexglue-sdk.git C:\dev\rexglue-sdk
   cd C:\dev\rexglue-sdk; git submodule update --init --recursive --depth 1
   # This project's SDK patch (vsync option, no continuous repaint; see notes below)
   git apply <path to this repo>\patches\rexglue-sdk-v0.10.1-present.patch
   # Windows checks out git symlinks as text files; libmspack needs real copies (see notes below)
   . C:\dev\vsenv.ps1; cmake --preset win-amd64 -DREXGLUE_ENABLE_FIDELITYFX=ON
   cmake --build out/build/win-amd64 --config Release --target install
   cmake --build out/build/win-amd64 --config RelWithDebInfo --target install
   ```
3. Extract the disc into `game/`:
   ```powershell
   python -I tools/xdvdfs.py "Jurassic - The Hunted (USA).iso" extract game
   ```

## Graphics

| Setting | Values | Default |
|---|---|---|
| `internal_resolution` | `auto`, `720p` (console), `1440p` (2×), `4k` (3×) | `auto`: matches your display |
| `upscaler` | `fsr` (AMD FSR 1), `cas` (AMD CAS), `bilinear` (also in the F2 panel, live) | `fsr` |
| `upscaler_sharpness` | `0.0`–`1.0` (FSR: 1 = sharpest; CAS: extra sharpening) | `0.9` |
| `antialiasing` | `off`, `fxaa`, `fxaa_high` (also in the F2 panel, live) | `off` |
| `framerate` | `30` (original), `60`, `120`, `144`, `165`, `185`, `240` | `30` |
| `vertical_sync` | `true` / `false` | `false` |
| `hdr_max_brightening` | `0`–`16`: how far auto-exposure may brighten (`0` = each level's own limit; also in F2) | `2.0` |

The 3D scene is rendered at an exact multiple of the console's 1280×720, so `4k` is a true
3840×2160 render, not an upscale. FSR applies when the window is larger than the internal
resolution (e.g. `1440p` on a 4K display); with `4k` on a smaller display the image is
supersampled down instead. Set these in `jurassichunted.toml` or on the command line
(`--internal_resolution=4k`). The SDK's lower-level options (`resolution_scale`,
`present_effect`, `present_fsr_sharpness_reduction`, `fullscreen`, `vsync`…) still work and win
if set.

Measured in the first level on an RTX 3080 / Ryzen 7 5800X with the frame rate limit at 165:
720p runs at the limit, 1440p at ~105 fps, 4K at ~55 fps (all hold the original 30 fps easily).
At 4K the GPU is at 100% load and frame time grows with the pixel count (render target and
resolve work through the Xbox 360 GPU emulation included). Of the SDK's GPU options only
texture filtering made a measurable difference, so at 4K the game's own filtering is used instead
of the SDK's forced 4x anisotropic (`anisotropic_override=-1`, +8%; an explicit setting wins). On
a 1440p display, 1440p internal is already native sharpness; 4K internal adds supersampling.
Record your own with `--log_level=debug` ("Frame rate: … fps" every 5 s) or `--perf_log_csv=<file>`.

### Anti-aliasing (and why there's no MSAA option)

`antialiasing` runs FXAA (the SDK's `swap_post_effect`: `fxaa`, or `fxaa_extreme` for
`fxaa_high`) on the rendered 3D image before it's upscaled. It costs ~0.4 ms per frame at 4K
(42.6 → 42.0 fps in the first level). The F2 panel switches it live; the SDK patch makes
`swap_post_effect` hot-reloadable by passing changes to the running command processor.

An MSAA setting isn't possible in this game. Logging every render target setup the game makes
(`RB_SURFACE_INFO` writes) shows its main scene is drawn without MSAA (pitch 1280, 1x) and its 4x
MSAA surfaces always have exactly half the width of a 1x one (640/1280, 520/1040, 400/800,
440/880). That's an Xbox 360 EDRAM trick, not anti-aliasing: a 640-wide 4x surface has the same
sample grid as the 1280-wide 1x depth buffer it's laid over, so half-resolution passes depth-test
against the full-resolution scene. Forcing those surfaces to 1x (tested by clamping the sample
count where the guest writes the register) gained ~15% at 4K but broke the image into black
tiles; 2x has the same mismatch. Adding MSAA to the main scene can't work either: 1280×720 at 4x
needs ~30 MB of EDRAM and the console has 10 MB, and the emulation follows the guest's EDRAM
layout. The internal resolution is the other anti-aliasing: above your display's resolution it's
supersampling (4K on a 1440p display = 2.25 samples per pixel).

**Fixed 2026-11-15:** `internal_resolution` never took effect before. The SDK's `resolution_scale`
belongs to the GPU plugin (`rexgpu-xenos.dll`), which is loaded after the app's startup hook, so
setting it there was silently rejected and the game always rendered at 720p (FSR then only
upscaled 720p, hence the soft image and text). `src/graphics_settings.cpp` now hands the value over
through the environment (`REX_RESOLUTION_SCALE`), which the SDK applies when the plugin registers
the setting; the log confirms it ("Graphics: rendering at 3840 x 2160 (resolution_scale 3)").

### Auto-exposure (the white glare in The Lost Castaways)

**Fixed 2026-11-17:** L08a, The Lost Castaways, was almost entirely white. The game's HDR
auto-exposure measures the scene's brightness by reading the rendered image back from the GPU,
which the recompiled renderer doesn't provide (the SDK's `readback_resolve` option does, but made
every level far too dark and cost frame rate). Without that measurement the exposure always sits at
the level's brightening limit ("HDR Max Brightening" in its `RenderParam` objects). Most levels
allow 1.3–1.5x, which looks right; L08a allows 16x, hence the white-out.

`hdr_max_brightening` (default 2.0) caps that limit where the renderer receives it: a hook at the
entry of its two HDR parameter setters (`sub_8213E3E8` target values, `sub_8213E468` current values;
`f3` = max brightening), which the level's `RenderParam` zones call every frame (`sub_822B6xxx`) and
Lua's `Renderer:SetHDRParam` also uses. L08a now shows its dark jungle with light shafts; other
levels are unchanged, since their own limits are below the cap. `0` restores the original behavior.
The F2 panel has a slider for it.

### Frame rate

The console game waits for two 60 Hz vblanks per frame, which is its 30 fps cap; its logic and
animation already run on real elapsed time. Above 30, the game turns off the emulated vblank wait
(`vsync=false`) and a hook just before the game's only `VdSwap` call (`JthFramePace` at
`0x824BA09C`, `src/framerate.cpp`) paces frames to the chosen rate with a high-resolution
waitable timer. Measured: 60 → 60.0 fps, 144 → 144.0 fps, game clock at 1.000× real time and the
intro's timing unchanged. 240 is a limit, not a guarantee: the recompiled game is CPU-bound at
roughly 200–210 fps on a Ryzen 7 5800X. It also switches live from the F2 panel (a change
notification on `framerate` turns the emulated vblank wait off or back on); an explicit `vsync`
in the settings file or on the command line wins over it.

**FPS counter** (`show_fps`, launcher: GRAPHICS, or F2): the game's own frame rate in the top left
corner, counted at the game's frame present (`JthFramePace`) and updated twice a second. It is drawn
with each game frame and asks for no extra repaints, so it doesn't change the rate it measures.

**Vsync** (`vertical_sync = true`, launcher: GRAPHICS → Vsync) presents each frame on the display's
refresh with no tearing, so the frame rate can't exceed the refresh rate (measured 163 fps at a
240 limit on a 165 Hz display). Upstream ReXGlue always presents immediately with tearing allowed;
the `present_vsync` option comes from this project's SDK patch (see Notes). The SDK's own `vsync`
setting is unrelated: it is the emulated console's 60 Hz vblank. Without vsync, frame rates above
the refresh rate are only shown when Windows lets the game tear (borderless fullscreen with no
overlays); otherwise it runs at the refresh rate as well.

**Overlays such as RTSS count presents, not game frames.** Before the SDK patch, any open ImGui
dialog (including the SDK's always-present achievement toast) made the window repaint as fast as
possible, so overlays showed ~200–320 "fps" even with the game capped at 30 or 165. Now the window
repaints once per game frame, and `--log_level=debug` logs both rates every 5 s ("Frame rate:" and
"D3D12Presenter: … presents/s").

**FSR 2/3:** the SDK's temporal FSR path needs real depth and motion vectors, which this game
doesn't provide; with synthesized ones the image came out blocky and smeared (worse than 720p).
`fsr2`/`fsr3` settings are treated as FSR 1, and the launcher no longer offers them. Rendering at
4K on a 1440p display with FSR 1 (supersampling) gives the sharpest image.

FSR needs the SDK built with `-DREXGLUE_ENABLE_FIDELITYFX=ON` (see setup above); the build copies
`amd_fidelityfx_dx12*.dll` next to the exe. Without it only `bilinear` is available and the game
logs a warning.

## Field of view and the PC Options panel

Press **F2** in game for the PC Options panel:

- **Field of view** (60–120 horizontal degrees at 16:9; the game's default is 86).
- **Mouse sensitivity**, the **weapon wheel** on/off and **toggle sprint**.
- **Upscaling**: AMD FSR 1, AMD CAS or off (bilinear), plus a **sharpness** slider (FSR's RCAS
  sharpness, or CAS's extra sharpness). Switches live, without a restart: the SDK patch makes the
  presenter re-read `present_effect` / `present_fsr_sharpness_reduction` /
  `present_cas_additional_sharpness` whenever they change. The panel also shows the internal
  resolution, which needs a restart and so stays in the launcher.
- **Anti-aliasing**: off, FXAA or FXAA (high quality), live (see
  [Anti-aliasing](#anti-aliasing-and-why-theres-no-msaa-option)).
- **Frame rate** (30–240) and the **FPS counter**.
- **Hide HUD**: just the game, with no crosshair, ammo, compass, objectives, messages, subtitles
  or button prompts (see [Hide HUD](#hide-hud)).
- **Display mode**: borderless, fullscreen (exclusive) or windowed, plus the window size when
  windowed. These are the SDK's own `fullscreen`, `fullscreen_exclusive`, `window_width` and
  `window_height` settings, which it applies to the window live.
- **Auto-exposure brightening limit** (see
  [Auto-exposure](#auto-exposure-the-white-glare-in-the-lost-castaways)).
- **Cheats**, including the super speed multiplier.

Everything applies instantly and is saved to `jurassichunted.toml` as soon as you finish a change
(sliders when released, checkboxes and choices right away, and again when the panel closes), so
nothing is lost if the game is closed with the panel open. Only the panel's own keys are touched
(`fov`, `weapon_fov_fixed`, `mouse_sensitivity`, `weapon_wheel`, `upscaler`,
`upscaler_sharpness`, `antialiasing`, `framerate`, `show_fps`, `fullscreen`,
`fullscreen_exclusive`, `window_width`, `window_height`, `hdr_max_brightening`, `cheat_*`); other
settings and comments are kept, and the launcher reads the same keys. Earlier builds saved only
FOV and sensitivity, and only when the panel was closed. While the panel is open, game input is
paused and the cursor is free.

**With a controller:** clicking the touchpad of a PlayStation controller (DualShock 4 or DualSense)
opens and closes the panel, like F2. The D-pad or left stick moves between options and A / cross
changes them; the game reads a neutral controller meanwhile (the SDK's UI input blocker). The touchpad
click normally shares the Guide bit with the PS button, so the SDK patch counts touchpad clicks on
their own (`rex::input::TouchpadClickCount`, from SDL's touchpad button) and the GUI update polls
that count.

You can also set `fov = 100` in `jurassichunted.toml` or pass `--fov=100`.

- Applies to the player's view only; cutscenes keep their original framing.
- Aiming down sights still zooms in proportionally.
- The first-person weapon keeps its normal size and position at any FOV ("Keep weapon size
  fixed" in the F2 panel, `weapon_fov_fixed`, on by default). The game draws the weapon with the
  world's projection but in its own near depth range (viewport Z [0, 0.01]); the SDK patch scales
  the clip-space XY of exactly those draws by `viewmodel_xy_scale`, which `JthCameraFov` sets to
  tan(new FOV / 2) / tan(game FOV / 2) each frame (1 in menus and cutscenes). The weapon therefore
  looks as the game would draw it without the slider, including its own aim zoom and sprint
  widening. Scaling in clip space (not the viewport) keeps clipping at the real screen edges, so a
  shrunk weapon isn't cut off at narrow FOVs.
- Sprinting widens the view by about 12°. The engine doesn't draw scenery past a horizontal FOV
  of about 127° (view slope 2.0), which showed up as two see-through bars at the screen edges when
  sprinting at a high setting, so the final FOV is capped at 126°.

How it works: `Camera::Update` (`sub_82260948`) widens the stored 70° (4:3) FOV to 86° for 16:9
and passes it to the perspective builder `sub_822640F0`. A mid-function hook at `0x82260A98`
(`JthCameraFov` in `src/pc_options.cpp`) rescales that value for the player camera in tangent
space.

## Hide HUD

`hide_hud = true` (launcher: GRAPHICS → Hide HUD, or F2; applies live) hides everything the game
draws over the picture: crosshair, ammo, grenades, compass, objectives, messages, subtitles and
button prompts. Menus, the pause screen and cutscenes are unchanged.

The HUD is the GUI page `hud` (`gui/hud.xml`), loaded twice: by the player's HUD object
(`ActorHud_SPBase`, at ActorProperties +196, its page at +4) and by the GUI manager. Both are shown
and hidden with `GuiPage::SetVisible` (`sub_8211CC48`: r3 = page, r4 = visible; visible flag at
page +22, name at +4). `src/hide_hud.cpp` hooks its start (`JthGuiPageSetVisible`, `0x8211CC58`).
It notes what the game asks for each `hud` page and turns a "show" into "hide" while the option is
on. Once per frame (GUI update) it also hides any `hud` page still showing. Turning the option off
shows a page again only if the game last asked for it, so a HUD hidden by a cutscene stays hidden.
`World:ShowGuiPage(false, "hud")` from Lua isn't enough: it only reaches the GUI manager's copy,
and the game shows it again.

## Cheats

Toggle in the launcher's CHEATS tab or the **F2** PC Options panel, or set `cheat_god_mode`,
`cheat_infinite_ammo`, `cheat_infinite_adrenaline`, `cheat_infinite_grenades`,
`cheat_one_hit_kill` to `true` and `cheat_super_speed` to a multiplier (`1` = off, up to `4`) in
`jurassichunted.toml` / on the command line. Implemented in `src/cheats.cpp`; every object is
checked against its known vtable before anything is written.

| Cheat | How |
|---|---|
| Infinite ammo | keeps the current firearm's magazine (item +616) at capacity (+612); for the plasma gun, also its charge (see below) |
| Super speed | multiplies the player's input speed modifier where the movement step reads it (see below) |
| God mode | sets the game's own `Invincible` flag (Actor +228) and refills ActorProperties health |
| Infinite adrenaline | keeps `gpAdrenalin`'s meter (+24) at max |
| Infinite grenades | twice a second, tops the frag grenades back up to 5 through the game's own Lua (`Inventory:GetBulletCount` / `AddBullet` with `models/weapons/grenade_frag_d/grenade_frag_d.xml`, as `weapons.lua` adds them) |
| One hit kill | damage the player deals is raised to 1,000,000 in the three damage paths (see below) |

One hit kill hooks each place damage is applied, and only changes damage whose attacker is the
player (a bullet's shooter is at bullet +212) and whose victim isn't:

- `ActorProperties_SPBase` apply-damage (`sub_82368F98` at `0x823692E4`, `f30` = final damage),
- the plain `ActorProperties` one (`sub_822D7510` at `0x822D7520`, damage info +24),
- `Animal::Damage` (`sub_822EF018` at `0x822EF114`, vtable slot 90): dinosaurs keep their health at
  animal +412 and don't go through ActorProperties at all.

Verified: with the cheat off, a frag grenade throw leaves 4 of 5; with it on the count stays at 5.
A raptor in L15 dies from the first shot ("damage (animal) ... -> one hit kill" with
`--log_damage=true`).

**The plasma gun** (the reward for collecting the gun parts) has no reserve and doesn't reload from
one: `wsModeReloadPlasmaGun` (vtable `0x82030BCC`) keeps a charge in seconds (mode +68, full at
+72 = magazine capacity × `bullet_load_time`, 5 × 2 s), each shot spends one load time of it and
time refills it, and its update (`sub_82373A50`) sets the loaded rounds to charge ÷ load time
every frame. So topping up the magazine alone was undone a frame later and the count still went
down. A hook at the start of that update (`JthPlasmaCharge`, `0x82373A64`) keeps the charge of the
player's gun in hand full while infinite ammo is on. With `--log_ammo=true` the log shows the
gun's recharge state ("ammo: plasma recharge ... load time 2.00 charge 10.00 / 10.00") and each
refill.

**Super speed:** `csControllerActor`'s movement step (`sub_82241E10`) multiplies the movement input
(controller +76/+80/+84) by the controller's input speed modifier (+264, what the script command
`scSetInputSpeedModifier` sets) before handing it to the animation-driven locomotion. A hook right
after it loads that modifier (`JthMoveSpeed`, `0x82242054`) multiplies it for the player's
controller (`csControllerActorPlayer`) only. Sprinting goes through the same step, so it's scaled
too, and the character controller still handles collisions. Measured top speed in L08c (player
position at Actor +0x50/+0x58): 3.5 m/s normally, 7.0 at 2x, about 11 at 3x and 14 at 4x.

## Controls

Keyboard and mouse work alongside a controller; use either at any time. Mouse look is applied
directly to the camera (raw, 1:1, no stick acceleration or aim assist). It is captured while
you're in gameplay and released automatically in menus, cutscenes, the pause menu, or when the
window loses focus.

| Action | Key | Controller |
|---|---|---|
| Move / strafe | W A S D | Left stick |
| Look | Mouse | Right stick |
| Fire | Left mouse | RT |
| Aim (hold) | Right mouse | LT |
| Jump | Space | A |
| Crouch | C or Left Ctrl | B |
| Reload | R | X |
| Change weapon (next) | Tap Q, or mouse wheel | Y |
| Weapon wheel | Hold Q, point with the mouse, release (or left-click); right-click / Esc cancels | |
| Pick a weapon | 1–9 (the n-th weapon carried) | |
| Throw grenade | G | RB |
| Adrenaline | F | LB |
| Sprint | Left Shift | Left stick click |
| Melee | V or Mouse 4 | Right stick click |
| Interact | E | D-pad |
| Objectives | Tab | Back |
| Pause | Escape | Start |
| Skip video / cutscene | Space, R, Esc or left click | A, X or Start |
| Balance (fallen trees, beams) | A / D, ← / →, or mouse left/right | Right stick ← → |
| Menus | Mouse (point, click, right-click back, wheel), arrows, Enter (accept), Backspace or Escape (back) | |

**Toggle sprint** (`toggle_sprint`, off by default; launcher: CONTROLS, or F2): one press of sprint
(left stick click or Shift) keeps you sprinting until you stop moving (stick near the center for
0.3 s) or press it again. The game itself only sprints while the button is held, so
`src/pad_filter.cpp` keeps the button held in the state the game reads while the toggle is on
(SDK patch: `InputSystem::SetGuestStateFilter`). Measured in L17: the same 5.0 m/s sprint as
holding the button.

**Weapon wheel** (`weapon_wheel`, on by default; launcher: CONTROLS, or F2): holding the
change-weapon key for more than ~0.2 s opens a radial menu of the weapons you carry: a picture of
each, its name, its slot number and the rounds in its magazine, with the one in hand marked. Move
the mouse toward a weapon and release the key (or left-click); right-click or Esc cancels. A quick
tap still switches to the next weapon (on release), and number keys that aren't bound to anything
else pick weapons directly.

- **On a controller:** hold Y (triangle on a PlayStation controller) for the same wheel; the left
  stick points at a weapon, releasing the button switches to it and B / circle cancels. A tap still
  switches to the next weapon. The SDK patch adds `InputSystem::SetGuestStateFilter`, a hook on
  the state the game reads (not the one SDK dialogs read). `src/pad_filter.cpp` hides Y from the
  game while it's down, replays a tap as a 100 ms Y press, and hides the left stick (so the player
  stands still) and B while the wheel is open. The keyboard's own Y pulses (a Q tap, a mouse-wheel
  notch) pass straight through.
- **Pointing:** the mouse moves a pointer (scaled by `mouse_sensitivity`, so the same hand movement
  works at any DPI) instead of the camera, and firing/aiming are held back while the wheel is open.
  Movement already counts from the moment the key goes down, so a quick press-and-flick picks the
  weapon you flicked toward. Small movements near the center don't change the choice, and a
  highlighted weapon stays highlighted until the pointer is clearly past its edge.
- **Pictures:** the game has no weapon pictures (it even asks for three files, e.g.
  `gui\textures\weapons\mossberg.dds`, that aren't on the disc), so the wheel draws side-view
  silhouettes made for this project (`src/weapon_art.cpp`). To use pictures of your own, put PNGs in a
  `weapon_images` folder next to the game, named after the weapon's folder: `ass_bar`, `ass_m249`,
  `ass_scar`, `pis_colt1911`, `pis_glock18c`, `pis_smith`, `plasmagun`, `rif_coltrifle`, `rpg7`,
  `sho_future`, `sho_mossberg`, `sil_crossbow`, `sni_whitworth` (e.g.
  `weapon_images\sho_mossberg.png`; transparent backgrounds look best, any size up to 4096×4096).
  They're loaded the first time the wheel shows that weapon.
- **Switching:** the game's controls only have "next weapon", so `src/weapon_wheel.cpp` reads the
  inventory's slots (`wsInventory` +44 → `{count, capacity, items[]}`, current item +152; the
  empty-hands `no_weapon` item is left out) and answers the player controller's own `ChangeNext`
  / `ChangePrev` input queries (from `0x821BE00C` / `0x821BE044`; `ChangePrev` exists in the game
  but is bound to nothing) until the chosen weapon is in hand, taking the shorter way round. The
  game's own animation, sounds and rules apply.

**Fixed 2026-11-17: the wheel could pick the wrong weapon.** The pointer was 100 raw mouse counts
across with a 25-count dead zone, a few millimetres of hand movement, so a slight drift while
releasing the key could land on a neighbouring weapon, and a flick made before the wheel appeared
turned the camera instead. A switch that needed two "next" presses also sent the second one while
the first switch was still animating, which the game drops (Mossberg → Whitworth took three presses
and two seconds). Now the pointer is larger and sensitivity-scaled, starts with the key press and
has a dead zone and sticky sector edges; each press waits until the previous switch has settled;
and "previous weapon" makes every switch with up to three weapons a single press.
`--log_weapon_wheel=true` logs the slots, every press and each switch;
`--weapon_wheel_direction=1` / `-1` forces next-only / previous-only (testing). Keyboard and mouse
only; the controller's Y still cycles.

Rebind keys (the `[bind]` section) and change mouse sensitivity in `jurassichunted.toml` next to
the exe; see
[config/jurassichunted.example.toml](config/jurassichunted.example.toml). Invert look follows the
game's own Options setting.

How it works: `src/pc_input.cpp` adds a keyboard/mouse device that feeds the game's controller
input, plus a mid-function hook in the player's look update (`sub_821C7EB0` at `0x821C80CC`,
declared in `config/default.toml`) that adds mouse movement to the frame's yaw/pitch deltas in
radians. While the mouse moves, the device also reports a right-stick deflection (and the hook
discards the stick's own turn) so scripted checks such as the "look around" tutorial step see look
input.

**Balancing** (the fallen tree in L04 "Far from Shore, Far from Home", the lava fields in L13; the
prompt shows "RS ← →", or your A / D keys with keyboard prompts): stepping onto a
`Models\General\balance_start` prefab calls `csControllerActorPlayer:StartBalance(prefab,
difficulty)`, which sets the player controller's `+841` flag. While it's set, the look update runs the balance code (`sub_821C26A8`: first an
automatic walk onto the beam, `+840`, then the balance) instead of the normal look, and the
balance steers with `LookHorizontal` (right stick X, ±1000). Before the fix nothing on the keyboard
reached it, and the mouse was even released (the normal look update, which keeps PC gameplay state
alive, doesn't run). Now `src/menu_mouse.cpp` wraps `sub_821C26A8` and adds A/D, ←/→ and
horizontal mouse movement to the `LookHorizontal` queries made inside it: keys ramp to a full push
over 0.25 s (a tap is a small correction, holding tips you over within ~2 s, like holding the
stick), mouse speed steers proportionally. The wrapper also keeps the mouse captured and applies
the cheats while balancing. Testing: `--dev_balance_skip_walk=true` finishes the walk at once; in
L04, `lua local c = csControllerActorPlayer:cast(BaseActor:cast(world:GetPlayerActor()).ControllerActor) for id = 1, 400000 do local o = world:GetObjectByID(id) if o then c:StartBalance(TransformObject:cast(o), 0) end end`
starts the first balance (only balance prefabs are accepted).

## Button prompts

`button_prompts` (launcher: CONTROLS → In-game button icons) picks the icons in the game's own
prompts; it applies when the game starts.

- `xbox`: the original icons.
- `playstation`: ✕ ○ □ △ for A B X Y, R1/L1 for RB/LB, and a PlayStation D-pad ("✕ ACCEPT").
  Drawn at startup in `src/button_prompts.cpp`, at the size each icon is shown (4x4
  supersampled), so they need no image files and are in every build: dark round buttons with a
  light rim and the coloured symbol (blue ✕, red ○, pink □, green △), L1/R1 as pills, the D-pad's
  four arrow pads with "up" lit (the game turns that tile for each direction), and the right
  stick with an R for the balance prompt. Artwork made for this project.
- `keyboard`: keycaps showing your bound keys: A = Space (jump), B = C (crouch), X = R (reload),
  Y = Q, LB = F, RB = G ("SPACE ACCEPT", "R CREDITS"). `pc_input.cpp` maps each key to the same pad
  button everywhere, so the key shown always works (Enter/Esc also work in menus). The D-pad tile
  is drawn as an arrow key, because the game flips/rotates that one tile for all four directions.
  Labels are rendered at startup with a Windows system font (Segoe UI Bold) through stb_truetype.
  The balance prompt's "RS" (`gui\textures\xbox\controller_tilt1.dds`) shows your strafe keys
  ("A / D"); with `playstation` it shows a PlayStation right stick.

Where the icons come from: the menu toolbars use `$style_a` … and text uses `{IMG_A}` … tags
(`Language\TextLib.eng`, e.g. "Press {IMG_B} to pick up"), both defined in `gui/globals.xml` as
regions of `icons.dds`; larger prompts use `icons_big.dds` / `icons_big_2.dds`, and the HUD uses
`icons\bumper.dds` (RB/LB) and `icons\directional.dds` (D-pad). The game's file layer reads these
from `startup.xds` (an identical copy also sits loose in `game\Gui\Textures`) and prefers an
`xbox\` variant of a file when one exists (`icons\xbox\bumper.dds`).

How: at startup `src/button_prompts.cpp` decodes the installed loose originals, clears each button
cell, draws the PlayStation symbol or keycap over the area the Xbox button covered and
re-encodes the changed DXT5 blocks, all in memory. `src/game_files.cpp`
hooks the game's stream open/read/close (`sub_82130F08`, `sub_82130378` and its two returns,
`sub_82130598`) and, right after the game reads one of these files, swaps in the PlayStation
version, only if the bytes read match the original. Nothing is written to disk and the installed
game files are never changed.

Not covered: the controller diagram in the game's Options → Controls screen
(`controller_xbox.dds`) stays an Xbox 360 pad, and buttons named in words ("Use Right Stick to look
around", "Please reconnect the Xbox 360 Controller") stay as written.

## Mouse in menus, and skipping

The menu engine still contains the pointer code of the Wii/PC versions: every page has hit
rectangles, and "pointer moved" focuses the element under the pointer. Nothing fed it on Xbox 360;
`src/menu_mouse.cpp` does, from a wrapper around the GUI manager's update (`sub_82126880`):

- Moving the mouse highlights the menu item under it (position mapped into the 1280x720 GUI
  space, letterbox-aware, and written to the manager's pointer fields).
- Left click on an item accepts it; a click on empty space does nothing. Right click goes back.
  The wheel moves the selection up/down. In menus the mouse buttons don't also fire/aim.
- Clicks and the wheel are delivered by answering the game's own input-action queries
  (`sub_821BC8A0`: "Accept", "Back", "Up", "Down"), so they behave exactly like the pad buttons.

Skipping: videos already skip on A / Start and in-game cutscenes on A (`SkipCutscene` is bound to A
in `config\key_binding.txt`). X and a left click now skip too: on video pages they answer "Accept",
and outside menus they answer "SkipCutscene" (harmless when nothing is playing; Jump on A sends it
constantly). Verified on the intro video (skips within ~50 ms); in-level cutscenes use the same
action but weren't reachable in automated tests.

**Focus:** the PC controls only read the keyboard and mouse while the game has them: it must be
the foreground window and not be covered by a system overlay. Whenever that stops (Start menu,
Alt+Tab, Win+Shift+S, the Xbox Game Bar) the mouse is released, shown and unclipped right away
(checked every input poll as well as on the window's focus events), and it's captured again when
you come back. The log says which program took focus ("PC controls: SearchHost.exe took focus;
mouse and keyboard released", "game has focus again", "mouse captured for gameplay").

- **Game Bar (Win+G)** never takes focus from the game, so focus events don't fire; it's detected
  as a large window of another process at the center of the game window (click-through overlays
  such as FPS counters are skipped by `WindowFromPoint`).
- **Mouse look dead after coming back (fixed):** if the pointer was over the Start menu or Game Bar
  when you returned to the game (e.g. with Escape or the Windows key), mouse look got no motion at
  all and an arrow stayed in the middle of the screen until the next focus change. SDL 3 only
  delivers relative motion while it believes the pointer is over the window; enabling relative mode
  after a mouse capture made SDL drop the capture again, and dropping a capture clears that belief
  whenever Windows hasn't re-tracked the pointer since it left. `src/pc_input.cpp` now enables
  relative mode before the capture request (and releases in the reverse order), after an SDL warp
  to the window center that also hands the OS pointer back to the window.

To check it: start a level, press the Windows key (`SendInput`), move the
pointer onto the Start menu, press Escape, then move the mouse: `GetCursorInfo` must report no
cursor and the clip must be the window center, and the debug log must show mouse motion
("stand-in right stick on").

Test commands: `pointer <x> <y>` (GUI units), `click [left|right]`, `wheel <up|down>`;
`--menu_mouse_debug=true` logs what the pointer hits. The game window only receives keys while
focused (SDL), so automated tests toggle the F2 panel with `set pc_options_toggle_test <n>` (each
new value toggles it) instead of posting F2.

| 6 | L08a | The Lost Castaways | | 13 | L17 | The Final Piece |

Survival is `maps\Survival01`. Levels are `.cew` files; each one's scripts are compiled Lua 5.1
chunks embedded in it (`[BoxTrigger - 317240]`, `[KeyPointScript - 74]`, ...), driven by trigger
events (`BaseObject:cast(obj):OnEvent("OnEnter", sender)`); `world:LevelEnd()` ends a level.

**Fixed 2026-11-16: script errors were fatal.** The game's own level scripts contain errors that the
Xbox 360 caught and ignored (e.g. L13: `[PrefabPosition - 136683]:16: attempt to index global
'Event' (a nil value)`; L17: `[PrefabPosition - 219802]:8: Mesh: Attempt to cast nil value.`).
Lua catches errors with `setjmp`/`longjmp`, and the recompiler only handles those when told where
they are (`setjmp_address` / `longjmp_address` in `config/default.toml`); this project hadn't set
them, so the guest `longjmp` was translated as an ordinary function that couldn't jump back. Any
script error then ended in `PANIC: unprotected error in call to Lua API` and the game quit
(`0x80000003`). L13 and L17 crashed this way while loading, and it's the likely cause of the crash
at the end of the first level (not reproduced directly: the ending depends on the player's
position). With the addresses set, all 14 maps load and play.

- Script errors are now logged as warnings ("Lua error (status 2): ...", up to 200 per session,
  repeats skipped) from a hook in `luaD_throw` (`JthLuaThrow`, `src/dev_lua.cpp`).
- Every log notes the level being loaded ("Map: maps\l02\l02.cew").
- A hard crash writes "CRASH: <what> at <module>+<offset> ..." to the log, flushes it and saves a
  minidump (`logs\crash_<date>_<time>.dmp`; `src/crash_log.cpp`). `--debug_crash_test` (set it to
  true while running) crashes on purpose to test this.

Testing a level: `--dev_level_list=true` and the `lua` test command (see
[Automated testing](#automated-testing)). For example, the end of L02:
`lua local o = BaseObject:cast(tgObjectives) o:OnEvent('OnCompleteObj3', o)` then
`lua world:LevelEnd()` loads L04. Note that a test script line can't contain `;` (the command
separator), and methods are called with `:`.

## Tools

- `tools/xdvdfs.py`: list or extract files from the Xbox 360 disc image.
- `tools/xexinfo.py`: dump XEX2 headers (imports, libraries, compression).
- `tools/xex_extract.ps1`: decrypt and decompress `default.xex` to a raw image (`build/default.bin`)
  for disassembly with `C:\dev\rexglue-sdk\tools\binutils\powerpc-none-elf-objdump.exe`
  (`-D -b binary -m powerpc:common64 -EB --adjust-vma=0x82000000`).
- `tools/find_missing_funcs.py`: find code pointers (in vtables/function tables, or built in code
  with `lis`/`addi`) that miss a recompiled function start: the usual cause of
  "Call to invalid or unregistered function". Run with `--toml --config config/default.toml`
  after a build to get new `[functions]` entries; review each before adding.
- `tools/capture_window.ps1`: screenshot just the game window by process id.

### Automated testing

Launching with `--test_input_file <path>` adds a scripted controller (see `src/test_input.h` for
the command syntax: `tap a`, `hold lb+rb 500`, `stick l 0 1 2000`, `key space`, `mouse 300 0`,
`wait 1000`…). It's merged with any real controller, so normal play still works. `key` and
`mouse` drive the keyboard/mouse path without touching the real devices.

- `tools/test_session.ps1 -Commands "tap start; wait 3000; tap a; wait 6000; tap start" -Watch 50 -Shot shot.png`
  starts a fresh session, waits for the title screen, runs the commands, and reports any crash.
  (That sequence goes from the title screen to the first level.) Test runs use their own saves in
  `out\test_profile` (`-UserData ""` uses the real ones), and never delete logs.
- `tools/drive.ps1 -Commands "stick l 0 1 3000" -Wait 4 -Shot shot.png` sends more commands to the
  running session and takes a screenshot. `set fov 110` changes a setting live.
- `tools/post_key.ps1 -VirtualKey 0x71` posts a key (here F2) to the game window, for testing
  hotkeys without focusing it.
- `tools/xref.py build/default.bin <address or "string">` finds code that references an address
  or string (handy for locating game logic by its debug strings).
- `--dump_game_files="gui\textures\icons.dds,gui/globals.xml" --dump_dir=<folder>` saves those
  files as the game reads them, including ones packed in the compressed `.xds` archives
  (`src/game_files.cpp`).
- `--dev_level_list=true` makes the main menu's LEVEL SELECTION open the game's own developer
  map list (page `maplist_2`, also behind its hidden "LEVEL SELECTION DEBUG" button): every map in
  `scripts\maps.xml` order, locked or not, loaded directly by row (`$CORE.play_map`). Click LEVEL
  SELECTION with `pointer 270 438; click left`, then `tap down` N times and `tap a`. The redirect
  is a same-length text patch applied as the game reads `gui\mainmenu.xml`
  (`jth::files::AddPatch`).
- `--log_game_files=true` logs every file the game opens, including files inside its `.xds`
  archives, to find paths for `--dump_game_files`.
- `--log_input_actions=true` logs which game code (return address) queries which input action,
  once per pair and again when one first reports a value: how the balance's `LookHorizontal`
  query (from `0x821C29D8`) was found.
- `--log_damage=true` logs every damage calculation (victim, health, attacker, and whether one hit
  kill changed it); `--log_weapon_wheel=true` logs the inventory's weapon slots and each switch.
- Test command `key q 2000 mouse 0 80 600` holds keys and moves the mouse partway into the hold
  (here: opens the weapon wheel, then points down).
- `--log_lua_chunks=<text>` logs the Lua chunks the game compiles whose code contains `<text>`
  (`*` = all), e.g. `StartBalance` finds the prefab scripts that start balancing.
- Test command `lua <code>` runs Lua in the game's own script state on the game thread; results and
  errors are logged ("lua: ..."). E.g. `lua return type(World)`, `lua World:LevelEnd()`
  (`src/dev_lua.cpp`: script manager at `[0x8274D6FC]+48`, Lua 5.1 API addresses in the comments).
- `tools/dds.py topng in.dds out.png` converts the game's DDS textures (DXT1/DXT5/A8R8G8B8) for
  viewing; `tools/import_glyphs.py` imports controller button images (see the launcher section).

## Notes

- **SDK patch:** this project needs some small changes to ReXGlue v0.10.1, kept in
  `patches/rexglue-sdk-v0.10.1-present.patch` (apply in `C:\dev\rexglue-sdk` with `git apply`,
  then rebuild and install the SDK, both Release and RelWithDebInfo): a `present_vsync` option for
  the D3D12 swap chain; `ImGuiDialog::WantsContinuousRepaint()` so idle dialogs (the achievement
  toast) no longer make the window repaint continuously; live `present_effect` / sharpness
  changes (`Presenter::ReloadGuestOutputPaintConfigFromCVars`, used by the F2 panel);
  `viewmodel_xy_scale` / `viewmodel_depth_range` in `graphics/util/draw.cpp` (fixed weapon size);
  live `swap_post_effect` changes in `graphics/graphics_system.cpp` (FXAA in the F2 panel); and
  `rex::input::TouchpadClickCount()` (`include/rex/input/touchpad.h`, counted in
  `input/sdl/sdl_input_driver.cpp`), so a PlayStation controller's touchpad can open the F2 panel;
  and `InputSystem::SetGuestStateFilter` (`input/input_system.cpp`), which lets the app rewrite
  the controller state the game reads (controller weapon wheel, toggle sprint).
- **GPU plugin settings** (`resolution_scale`, `anisotropic_override`, `vsync`, ...) live in
  `rexgpu-xenos.dll`, which registers them only when it loads, after `OnPreSetup`. Setting them
  there is silently rejected; hand them over through the environment (`REX_<NAME>`, applied when
  the plugin registers) or set them in `OnPostSetup` if they're read every frame.
- **Git symlinks on Windows:** after cloning the SDK, any submodule symlink (mode `120000`) is a
  text file containing its target path. `libmspack/cabextract/mspack/*` must be replaced with copies
  of `libmspack/mspack/*` or the SDK fails to compile `lzxd.c`.
- **Controlled folder access:** the SDK's default user folder is `Documents\jurassichunted`. With
  Windows Defender's Controlled folder access enabled, writes there are blocked and startup aborts
  (`0xC0000409`). The app now defaults to `%LOCALAPPDATA%` instead.
- GPU emulation is the `xenos` plugin (`rexgpu-xenos*.dll`), enabled by default in `src/jurassichunted_app.h`.
